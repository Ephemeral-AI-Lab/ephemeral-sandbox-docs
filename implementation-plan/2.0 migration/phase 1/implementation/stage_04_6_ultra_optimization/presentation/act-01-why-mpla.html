Architecture/Why
Act 01 · Pressure

Agents publish faster than human-sized histories

When many agents fork, mutate, and publish in parallel, the checkpoint graph can grow much faster than a traditional container-image workflow expects.

The problem is not “a 10 GiB repository.” It is multiplying that repository by history depth, active writers, or publication copies.

Multiagent geometry

Three growth axes collide

Logical ancestry, physical bytes, and active write ownership grow for different reasons. Treating them as one layer list makes the kernel, disk, and heap pay for the same history repeatedly.

The architectural answer

History, bytes, and execution must scale separately

MPLA uses distinct authorities so each dimension can be optimized without corrupting another.

LogicalMerkle roots

Immutable, backend-neutral history. A new small edit creates new pages only along affected paths.

PhysicalLocator generations

A payload can be readable from an adopted allocation, a pack, or both during safe replacement.

RuntimeProjection recipes

OCI, a future microVM adapter, or another executor can realize the same root through different mechanisms.

This is why OverlayFS stops being the core. It remains the best qualified OCI mount adapter for now, but it no longer defines checkpoint identity or durable storage layout.

Not “issue free.” OOM, inode pressure, mount failure, and ENOSPC remain possible in any real system. MPLA makes them much less likely by bounding resident work, descriptors, active allocations, and projection depth—and by rejecting before partial state.
