Architecture/Three-plane model
Act 02 · Boundaries

Ask three different questions

A canonical root identifies meaning. A locator generation finds durable bytes. A projection receipt proves that one runtime can expose those bytes efficiently.

The root never embeds a pathname, AllocationId, locator generation, carrier identity, or OverlayFS mount structure.

Identity flow

The Merkle root describes meaning—not placement

Content identity and location identity are deliberately different types. That is what allows evacuation, repacking, cache eviction, and backend migration without rewriting history.

Allowed in canonical records

Names, object types, normalized metadata, file content payload digests, hardlink identity, and attribution digests.

Forbidden in canonical records

Absolute paths, allocation handles, backend device IDs, carrier names, mount order, locator generations, worker identity, and cache state.

Result: moving payload p7 from promoted allocation A into pack P9 does not change any root.

Runtime realization

OCI sees a shallow projection—not the full history

The runtime recipe is a cacheable proof that a small set of native directories realizes one root under one qualified environment.

Do not confuse depths. D_proj is runtime projection depth. Merkle tree depth d is canonical path-tree depth. MPLA bounds the former; a delta update traverses the latter.
Adapter boundary

OverlayFS is the current OCI mechanism—not a permanent architectural dependency
