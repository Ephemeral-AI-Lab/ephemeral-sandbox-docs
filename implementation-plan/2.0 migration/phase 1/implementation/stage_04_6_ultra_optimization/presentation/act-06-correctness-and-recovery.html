Architecture/Correctness
Act 06 · Invariants

Fast without ambiguous ownership

Every optimization is subordinate to four proofs: immutable meaning, complete payload coverage, exactly one owner, and old-or-complete-new visibility across failure.

A fast sample is invalid if it loses metadata, hides deferred work, resumes a post-seal session, leaks an allocation, or needs more memory than the declared envelope.

Isolation

A clean fork creates metadata—not a repository copy

Inactive forks share the immutable root and, when available, its projection. Physical writable state appears only after activation admits a session.

Concurrency

Build in parallel; serialize only the final ref decision

Each publisher seals, adopts, constructs locators, and builds its candidate root outside the short ref writer section. A head advance does not automatically mean conflict.

Failure model

Durable phases turn retry into deterministic replay

Recovery begins from persisted operation state and selected generations, not from in-memory control flow or a convenient pathname.

Idempotency

The same request ID means the same operation

Request identity is scoped by operation kind and branch/ref. Reusing an ID with different bytes is an error, not a second chance to execute different work.

Same ID · same digestresume or replay exact result

Skip completed phases and return the durable terminal.

Same ID · different digestIdempotencyMismatch

Reject before another publication can mutate state.

Expired ID fenceOutcomeExpired

The retired operation ID is never executed again.

Publication and continuation are separate identities. A publication can commit even when optional activation fails. The activation result cannot rewrite the publication terminal.
Memory safety

Backpressure happens before memory exhaustion

Admission is itself part of correctness because a half-allocated rejected job creates ownership and cleanup ambiguity.
