EphemeralOS · Stage 04.6

One filesystem truth. Movable bytes. Disposable execution.

The Merkle–Promoted Locator Architecture lets hundreds of agents publish quickly without turning history into hundreds of kernel layers—or copying an entire repository at every checkpoint.

The central move: separate what a checkpoint means, where its bytes live, and how one runtime mounts it.

Logical history may grow without bound. Runtime projection depth, active writable state, and resident-memory work stay explicitly bounded.
The architecture in one view

Three planes answer three different questions

Most scaling failures came from asking one data structure—the layer stack—to carry history, storage, and execution at the same time.

01 · Canonical plane What filesystem state is this?

RootId + AttributionRootId identify an immutable Merkle checkpoint. They contain no path, allocation, or mount identity.

02 · Physical plane Where can its bytes be read?

Immutable locator generations map payload digests to packs or adopted stationary allocations.

03 · Runtime plane How can a worker execute it now?

A qualified adapter selects a shallow read-only projection and gives the session one fresh writable upper.

The operating loop

Execution produces one sealed delta—not another permanent runtime layer

Publication converts a private writable allocation into an immutable payload source, updates only affected Merkle paths, and commits the ref last.

The non-claim

MPLA does not make physics disappear

A cold worker must still obtain bytes. A lower-only write may still copy up a whole file. A 1 GiB file may still require a 1 GiB read/hash pass. MPLA’s win is that these costs are explicit, bounded, reusable, and no longer multiplied by repository history.

Honest fast path. Sub-20 ms or sub-100 ms targets apply to verified stored-state selection and small deltas. They do not describe cold reconstruction of a missing 1 GiB repository.
