Architecture/Lifecycle
Act 03 · State changes

Activate, execute, seal, adopt, commit

A session begins with selection, owns exactly one writable allocation, and ends by converting that allocation into immutable payload state before the ref moves.

Closing checkpoint: filesystem state survives. Process memory, open-FD position, sockets, timers, locks, and the old process tree do not.

Phase 02 · Execute

Each agent receives one fresh ownership domain

PayloadStore allocates the upper and workdir together inside its qualified arena. WorkspaceManager receives an epoch-fenced lease—not ownership of a host workspace copy.

Upper is writable only while leased. After sealing, the same directory becomes immutable PayloadStore-owned state. “Sealed upper” describes its origin; it is no longer an active OverlayFS upper.
Phase 03 · Discover

Fast evidence is a hint; scanning remains the fallback

A mutation journal can narrow work only when its epoch and coverage are complete. Any gap, overflow, bypass, or ambiguous rename broadens the scan.

Phase 04 · Publish

Publication is an explicit ownership state machine

Durable Sealing is the no-return boundary. Before it, an exact rejection can preserve or clean private workspace state. At or after it, recovery rolls forward under the same operation ID.

Phase 05 · Adopt

The bytes stay still while ownership changes

This replaces a host-dependent rename optimization with a backend-local compare-and-adopt protocol over a stable allocation.

Quiesce

Admit no new command or mutation.

Drain

Stop holder tree; close writable FDs/maps.

Unmount

Destroy merged view and retire workdir.

Flush

Sync and stability-check upper bytes.

Revoke

Fence the workspace lease epoch.

Adopt

CAS owner state to PayloadStore and issue receipt.

Phase 06 · Commit

Ref replacement is the publication linearization point

Large scanning, hashing, and locator construction occur outside the short ref writer section. The final compare-and-swap either exposes the complete paired root or exposes nothing.

MCTS interpretation. Each search node can point to an immutable root, fork cheaply, and publish independently. The “sealed upper” is useful to any multiagent tree search, but MPLA is not specific to MCTS.
